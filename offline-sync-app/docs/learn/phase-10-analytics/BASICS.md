# Phase 10 — Analytics SQL: Basics

Siblings: [FILES.md](FILES.md) · [QUESTIONS.md](QUESTIONS.md) · [learn index](../README.md) · analytics folder: [analytics/README.md](../../../analytics/README.md)

Goal of this phase: practise analytics SQL on a fake but realistic copy of FieldSync's data. It lives in its own database `fieldsync_analytics`, so it never touches the app's real database. Commands run from `offline-sync-app/`.

1. **analytics query**. An analytics query reads many rows to answer a business question, such as "how long does a sync take in the slow tail?". It is different from an app query, which fetches one record fast. Analogy: an app query is looking up one phone number; an analytics query is counting calls per hour for a year. In this project: [analytics/queries/](../../../analytics/queries/) holds 14 of them.

2. **seed data**. Seed data is fake rows inserted on purpose so you have something to query. It is deterministic: running it twice gives identical data, because its "randomness" comes from `md5(key)` and not from `random()`. Analogy: a recipe that always bakes the same cake. In this project: [analytics/seed/seed.sql](../../../analytics/seed/seed.sql), and `TestSeedIsDeterministic` in [analytics/analytics_test.go](../../../analytics/analytics_test.go).

3. **safety guard**. Both the seed script and the test refuse to run unless the database name contains `analytics`. The seed script starts by truncating tables, so a wrong database would lose data. Analogy: a lock on the "delete everything" button. In this project: the `DO $$` block at the top of [analytics/seed/seed.sql](../../../analytics/seed/seed.sql) and `run` in [analytics/analytics_test.go](../../../analytics/analytics_test.go).

4. **aggregate**. An aggregate function (`count`, `sum`, `avg`) squeezes many rows into one value per group. After `GROUP BY` you get one row per group and the individual rows are gone. Analogy: a class register reduced to "28 present". In this project: first step of most queries, e.g. the `daily` CTE in [analytics/queries/01_moving_avg_per_actor.sql](../../../analytics/queries/01_moving_avg_per_actor.sql).

5. **CTE (common table expression)**. A `WITH name AS (...)` block that gives a sub-result a name, so a long query reads top to bottom as small steps. Analogy: labelled steps in a recipe. In this project: every file in [analytics/queries/](../../../analytics/queries/), e.g. `ordered`, `flagged`, `numbered` in [analytics/queries/05_sessionization_islands.sql](../../../analytics/queries/05_sessionization_islands.sql).

6. **window function**. A window function computes a value for each row by looking at related rows, without collapsing them into one. `PARTITION BY` says which rows are related; `ORDER BY` says in what order. Analogy: each runner's lap time compared to the runner before them, while everyone stays on the results sheet. In this project: `avg(events) OVER w_rows` in [analytics/queries/01_moving_avg_per_actor.sql](../../../analytics/queries/01_moving_avg_per_actor.sql), and `lag(occurred_at) OVER (...)` in [analytics/queries/05_sessionization_islands.sql](../../../analytics/queries/05_sessionization_islands.sql).

7. **window frame (ROWS vs RANGE)**. The frame is how far back the window looks. `ROWS 6 PRECEDING` means the previous 6 rows; `RANGE ... INTERVAL '6 days' PRECEDING` means the previous 6 calendar days. If days with no activity have no row, the two give different answers. Analogy: "the last 7 entries in the diary" versus "the last 7 days". In this project: `w_rows` and `w_range` in [analytics/queries/01_moving_avg_per_actor.sql](../../../analytics/queries/01_moving_avg_per_actor.sql).

8. **row_number, rank, dense_rank**. Three ways to number rows in order. `row_number` is 1,2,3 with ties broken arbitrarily; `rank` gives ties the same number and then skips (1,2,2,4); `dense_rank` gives ties the same number without skipping (1,2,2,3). Analogy: medals at a race when two people tie for silver. In this project: [analytics/queries/02_top3_per_group_ties.sql](../../../analytics/queries/02_top3_per_group_ties.sql) computes all three side by side.

9. **percentile**. A percentile says "this share of values are at or below this number". p50 is the median; p99 means 99% of values are at or below it, so it describes the slow tail. Averages hide the tail. Analogy: "most trains are on time, but one in a hundred is hours late". In this project: `percentile_cont(0.99) WITHIN GROUP (ORDER BY secs)` in [analytics/queries/04_latency_percentiles.sql](../../../analytics/queries/04_latency_percentiles.sql).

10. **FILTER clause**. `count(*) FILTER (WHERE ...)` counts or averages only the rows that meet a condition, so several differently filtered numbers come out of one pass over the data. Analogy: counting red, green and blue sweets from one bag in one go. In this project: [analytics/queries/12_conditional_pivot_filter.sql](../../../analytics/queries/12_conditional_pivot_filter.sql).

11. **gaps and islands (sessionization)**. To split a stream of events into "sessions", mark each event that comes after a long silence as a new start, then take a running sum of those marks. The running sum is the session number. Analogy: starting a new page in a notebook each time you return after a break. In this project: [analytics/queries/05_sessionization_islands.sql](../../../analytics/queries/05_sessionization_islands.sql); a 30 minute silence starts a new session.

12. **cohort and retention**. A cohort is a group of people who started in the same week. Retention is the share of that group still active n weeks later. A grid of every cohort and every week makes dead cohorts show as 0, not as missing rows. Analogy: tracking how many students from the January intake still attend in March. In this project: [analytics/queries/07_weekly_retention_cohort.sql](../../../analytics/queries/07_weekly_retention_cohort.sql).

13. **funnel**. A funnel counts how many things reach each stage in order, so you can see where you lose them. Here: location opened, then assessment, then photo. Analogy: a sales funnel at a shop door, browsers, then buyers. In this project: [analytics/queries/06_funnel_location_assessment_photo.sql](../../../analytics/queries/06_funnel_location_assessment_photo.sql).

14. **LEFT JOIN trap**. `LEFT JOIN` keeps parent rows that have no children. An `INNER JOIN` silently drops them, and `count(*)` counts the empty row as 1; `count(child.id)` correctly counts 0. Analogy: a register that must include absent students. In this project: Q4 and Q8 in [analytics/QUESTIONS.md](../../../analytics/QUESTIONS.md).

15. **NOT IN and NULL**. `NOT IN (subquery)` returns no rows at all if the subquery contains even one NULL. `NOT EXISTS` does not have this problem. Analogy: one unreadable name on a guest list making the bouncer reject everybody. In this project: Q5 in [analytics/QUESTIONS.md](../../../analytics/QUESTIONS.md) (the file reports 0 rows vs 42 on the seed).

16. **integer division trap**. In Postgres `5/2` is `2`, not `2.5`, because both numbers are integers. Write `100.0` or cast to `numeric` before dividing to get a share. Analogy: a calculator that silently drops the decimals. In this project: Q2 in [analytics/QUESTIONS.md](../../../analytics/QUESTIONS.md).

17. **time zone safety**. A day boundary depends on the time zone. The queries first convert with `AT TIME ZONE 'UTC'` so the result does not change with the connection's `TimeZone` setting. Analogy: agreeing on one clock before counting "events today". In this project: `TestQueryResultsDoNotDependOnSessionTimeZone` in [analytics/analytics_test.go](../../../analytics/analytics_test.go).

18. **EXPLAIN**. `EXPLAIN` shows the plan Postgres will use for a query. `EXPLAIN (ANALYZE, BUFFERS)` also runs it and reports real time and how many 8 kB pages were touched. Analogy: asking a taxi driver which route they will take, and then timing the trip. In this project: [analytics/EXPLAIN.md](../../../analytics/EXPLAIN.md) and [analytics/explain/](../../../analytics/explain/).

19. **Seq Scan vs Index Scan**. A Seq Scan (sequential scan) reads every page of the table. An Index Scan uses an index to jump to the matching rows. For a few matching rows out of 50,680, the index plan touched 10 buffers instead of 3,063 in the project's measurement (one laptop, data in memory; order of magnitude only). Analogy: reading the whole book versus using the index at the back. In this project: [analytics/EXPLAIN.md](../../../analytics/EXPLAIN.md), query 1.

20. **bitmap and index-only scans**. A Bitmap Index Scan collects matching row locations from the index, then visits each table page once. An Index Only Scan answers from the index alone when it holds every needed column. Analogy: a shopping list sorted by aisle, versus a shopper who needs nothing but the price tags. In this project: query 1 and 2 use bitmap scans and query 3 an index-only scan in [analytics/EXPLAIN.md](../../../analytics/EXPLAIN.md).

21. **composite index**. An index on several columns, with the equality column first and the range or sort column second, for example `(aggregate_id, occurred_at)`. A B-tree can only seek on its leading column; a filter on a later column alone cannot use it that way. Analogy: a phone book sorted by surname then first name; you cannot look up a first name alone. In this project: [analytics/indexes.sql](../../../analytics/indexes.sql).

22. **index write cost**. Every index must be updated on every insert. The outbox table `domain_events` is written on every sync, so adding indexes is not free. The study says it did not measure this cost. Analogy: keeping the index at the back of a book up to date every time you add a page. In this project: "What this does not show" in [analytics/EXPLAIN.md](../../../analytics/EXPLAIN.md).

23. **invariant test**. Instead of comparing exact output, the test checks things that must always be true, for example "total sessions' events equal the total event count". Each query file has a matching check function. Analogy: checking that a till balances rather than reading every receipt. In this project: the `invariants` map and `TestQueryInvariants` in [analytics/analytics_test.go](../../../analytics/analytics_test.go).

24. **outbox backlog**. The `domain_events` table is an outbox: rows wait there until a relay publishes them (`published_at` is NULL until then). A growing count of old unpublished rows means events are not reaching consumers. Analogy: letters left in the out-tray that nobody collects. In this project: [analytics/queries/09_outbox_backlog_consumer_lag.sql](../../../analytics/queries/09_outbox_backlog_consumer_lag.sql). The stuck rows in the seed are planted on purpose; they are not findings about a real system.
