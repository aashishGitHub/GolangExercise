# Phase 8 — Two-way sync: Basics

Siblings: [FILES.md](FILES.md) · [QUESTIONS.md](QUESTIONS.md) · [learn index](../README.md) · full design doc: [two-way-sync.md](../../two-way-sync.md)

Goal of this phase: keep FieldSync "work items" equal to the issues in an outside SaaS tool (a Jira-like service), in both directions. All commands below run from the `offline-sync-app/` folder.

1. **Two-way sync**. Two systems each hold a copy of the same record, and a change in either one must reach the other. It is harder than one-way sync because each change can bounce back and forth. Analogy: two people editing the same shared shopping list on separate phones. In this project: [internal/twoway/apply.go](../../../internal/twoway/apply.go) (inbound) and [internal/twoway/loader.go](../../../internal/twoway/loader.go) (outbound).

2. **webhook**. A webhook is a web request the other system sends to you when something changes, so you do not have to keep asking. Your side exposes a URL and waits. Analogy: a courier ringing your doorbell instead of you walking to the depot every hour. In this project: [internal/webhook/handler.go](../../../internal/webhook/handler.go), route `POST /webhooks/{system}`.

3. **polling**. Polling means you ask the other system "what changed since last time?" on a schedule. It is slower than a webhook but it cannot be lost: if a webhook is dropped, the next poll still sees the change. Analogy: checking your mailbox every morning, even if the courier forgot to ring. In this project: [internal/twoway/extractor.go](../../../internal/twoway/extractor.go), `Extractor.Run`.

4. **HMAC signature**. HMAC is a short fingerprint made from a message plus a secret key that only the two sides know. The sender attaches it; the receiver recomputes it and compares. If it matches, the message came from someone holding the secret and was not altered. Analogy: a wax seal pressed with a ring only the sender owns. In this project: [internal/webhook/verify.go](../../../internal/webhook/verify.go), `Verifier.Verify`.

5. **raw bytes**. The receiver must compute the HMAC over the exact bytes it received, not over parsed-and-rewritten JSON. Rewriting can change spaces or key order, and then the fingerprint no longer matches. Analogy: checking a seal on the original letter, not on a retyped copy. In this project: [internal/webhook/handler.go](../../../internal/webhook/handler.go) reads the body with `io.ReadAll` and passes those bytes to `Verify`.

6. **constant-time compare**. A normal string comparison stops at the first wrong character, so how long it takes can leak how many characters were right. `hmac.Equal` always takes the same time. Analogy: a bank vault that takes exactly one minute to say "no", whatever digit you got wrong. In this project: `hmac.Equal` in [internal/webhook/verify.go](../../../internal/webhook/verify.go).

7. **replay attack**. An attacker records a real, correctly signed request and sends it again later. The signature is still valid, so it needs another defence. Here the timestamp is part of the signed text and the receiver rejects anything older or newer than a tolerance window. Analogy: someone photocopying your signed cheque and cashing the copy next month. In this project: `ErrStaleTimestamp` in [internal/webhook/verify.go](../../../internal/webhook/verify.go); window default `WEBHOOK_TOLERANCE` = 5 minutes in [internal/twoway/config.go](../../../internal/twoway/config.go).

8. **delivery id**. Each webhook carries a unique id (header `X-Webhook-Delivery`). The receiver uses it to recognise a message it has already seen. This project also signs the id, so an attacker cannot re-send a captured body under a different id. Analogy: the tracking number on a parcel. In this project: [internal/webhook/verify.go](../../../internal/webhook/verify.go) (`HeaderDeliveryID`, and the rule that the id may not contain a `.`).

9. **202 Accepted**. This HTTP status means "I got it and stored it; I have not finished the work". The webhook handler answers 202 quickly and leaves the real work for later. Analogy: a post office stamping "received" on your parcel without delivering it yet. In this project: `reply(w, http.StatusAccepted, ...)` in [internal/webhook/handler.go](../../../internal/webhook/handler.go).

10. **inbox table**. An inbox table is a database table where incoming messages are saved first and processed later. The handler only saves; a separate worker processes. A slow or broken step downstream then never makes the sender retry. Analogy: a physical in-tray on a desk. In this project: table `webhook_inbox` in [migrations/000003_two_way_sync.up.sql](../../../migrations/000003_two_way_sync.up.sql).

11. **idempotent**. An operation is idempotent when doing it twice has the same effect as doing it once. This lets you retry safely after a crash. Analogy: pressing a lift's "up" button again does not call a second lift. In this project: `InsertWebhookInbox` uses `ON CONFLICT DO NOTHING` in [sqlc/queries.sql](../../../sqlc/queries.sql).

12. **idempotency key**. A unique token you send with a request so the server can recognise a retry of the same request and replay its first answer instead of doing the work again. Analogy: a cheque number: the bank pays cheque 1042 once, however many times it is presented. In this project: the `Idempotency-Key` header, set to the domain event id in `Loader.Handle` in [internal/twoway/loader.go](../../../internal/twoway/loader.go).

13. **version gate**. Every issue in the outside system has a version number that only goes up. The gate accepts a change only if its version is higher than the last one applied, and it does this in one SQL `UPDATE ... WHERE last_version < new`. Late or duplicate messages are then ignored. This also handles out-of-order delivery (messages arriving in a different order than sent): a late old edit is ignored instead of overwriting a newer one. Analogy: a page counter: you ignore any page numbered lower than the one you are on. In this project: `AdvanceLinkVersion` in [sqlc/queries.sql](../../../sqlc/queries.sql), called from `Applier.Apply` in [internal/twoway/apply.go](../../../internal/twoway/apply.go).

14. **field ownership**. For each field, exactly one system is the "owner" and wins. Here title and status belong to the outside system; notes belong to FieldSync. Most conflicts then cannot happen at all. Analogy: in a shared household, you always pay the electricity bill and your flatmate always pays the internet. In this project: `DefaultOwnership` and `Ownership.Merge` in [internal/twoway/ownership.go](../../../internal/twoway/ownership.go).

15. **conflict**. A conflict here means a newer outside change touched a field that FieldSync owns. The outside edit to that field is not applied; our value is kept; the outcome is labelled `conflict`. Analogy: a colleague editing the cell you own in a shared sheet, and you keeping your value. In this project: `OutcomeConflict` returned from `Applier.Apply` in [internal/twoway/apply.go](../../../internal/twoway/apply.go).

16. **echo loop**. A change made by A is sent to B, B reports it back to A as a "new" change, A sends it to B again, and so on forever. Analogy: two people on a phone call who each keep repeating what the other just said. This project has three guards: field ownership, an origin filter, and echo memory. In this project: [internal/twoway/loader.go](../../../internal/twoway/loader.go) (origin filter) and `Applier.isEcho` in [internal/twoway/apply.go](../../../internal/twoway/apply.go).

17. **origin filter**. Each event records who caused it (`actor_sub`). Events caused by the outside system are tagged `system:mockjira`, and the Loader skips them so they are not pushed straight back. Analogy: not forwarding an email to the person who just sent it to you. In this project: `OriginActor` in [internal/twoway/apply.go](../../../internal/twoway/apply.go) and the first check in `Loader.Handle`.

18. **echo memory**. After FieldSync pushes a change, it remembers the version and a hash of what the server answered. When a webhook arrives with the same version and hash, it is recognised as our own write and dropped. Analogy: a receipt you keep for something you just posted. In this project: table `sync_pushed` in [migrations/000003_two_way_sync.up.sql](../../../migrations/000003_two_way_sync.up.sql), written by `Loader.Handle`.

19. **backoff with jitter**. When a call fails, wait before retrying, and wait longer after each failure (backoff). Pick the wait at random between zero and the current ceiling (jitter) so many clients do not all retry at the same instant. Analogy: people leaving a stadium through different gates at different times instead of all at once. In this project: `HTTPClient.delay` in [internal/twoway/client.go](../../../internal/twoway/client.go).

20. **Retry-After**. A response header where the server says how many seconds to wait before trying again, usually with status 429 "Too Many Requests". The client obeys it exactly instead of guessing. Analogy: a shop assistant saying "come back in ten minutes". In this project: `parseRetryAfter` in [internal/twoway/client.go](../../../internal/twoway/client.go); only the whole-seconds form is read.

21. **tombstone**. A deleted record is not removed; it is marked deleted (`deleted_at`) and kept. A poll that simply does not list an item proves nothing, so "missing" must never mean "deleted". Analogy: crossing a name off a list instead of tearing out the line. In this project: `UpsertWorkItem` with `Deleted` in [internal/twoway/apply.go](../../../internal/twoway/apply.go); column `deleted_at` in `work_items`.

22. **dead letter**. A message that keeps failing is moved aside after a set number of attempts, with its payload and the reason saved, so the queue keeps moving. Someone inspects it later. Analogy: the "undeliverable mail" shelf at the post office. In this project: table `sync_dead_letters`; written by `Worker.recordFailure` in [internal/webhook/worker.go](../../../internal/webhook/worker.go) and `Loader.deadLetter` in [internal/twoway/loader.go](../../../internal/twoway/loader.go).

23. **checkpoint and resume**. A long pull is cut into pages. After each page, the position (a cursor) is saved in the same database transaction as that page's changes. If the job stops, the next run continues from the saved cursor. Analogy: a bookmark. In this project: `sync_state` table and `Extractor.Run` in [internal/twoway/extractor.go](../../../internal/twoway/extractor.go).

24. **mock server**. A fake version of the outside system that runs in memory, so you can test without the real vendor. It can also fail on demand (429, 500) and send webhooks late, twice, or in reverse. Analogy: a flight simulator. Note: it is not real Jira; its payload shapes are invented. In this project: [internal/mockjira/mockjira.go](../../../internal/mockjira/mockjira.go), runnable via [cmd/mockjira/main.go](../../../cmd/mockjira/main.go).

25. **Lambda receiver**. The same webhook handler can run inside an AWS Lambda behind API Gateway instead of as a normal server. The Terraform for it is written and validated, but not deployed to a real account. Analogy: the same shop counter, moved into a vending machine. In this project: [cmd/webhook-receiver-lambda/main.go](../../../cmd/webhook-receiver-lambda/main.go) and [infra/terraform/modules/webhook/main.tf](../../../infra/terraform/modules/webhook/main.tf).
